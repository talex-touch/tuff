## 4. 产品规则

本节门槛、时间窗口和自动分数预算作为本次实施初始值，与下文验收场景一起锁定。

### R1. 一次有效使用有统一定义

一次用户明确触发、且对应操作已成功接受的主要动作，记为一次有效使用。应用或文件交给操作系统处理成功即可，不要求验证外部应用已经完成启动。

| 动作 | 计数边界 |
|---|---|
| 打开应用或文件 | 实际启动或打开接口确认已接受。缺失路径、失败返回和启动错误不计数。只安排了稍后执行还不算成功。 |
| 插件功能或插件推荐条目 | 功能成功触发、页面就绪或对应主要动作完成。激活状态与执行结果分开；“不需要激活”不等于失败。 |
| 剪贴板历史 | 用户明确应用或复制某条历史记录，写入成功后记对应条目的使用。普通剪贴板采集不计数。 |
| 内置动作或页面入口 | 用户明确触发且宿主确认成功。后台刷新和自动恢复不计数。 |
| 预览、选择和搜索展示 | 不增加有效使用次数。 |
| 取消或执行失败 | 不增加有效使用次数；未选择某个推荐也不等于取消。 |

同一次动作经过多个回调、入口或进程，只计一次。动作重试不得重复累计。用户主动再次触发并成功，是新的一次使用。

应用的“启动次数”只记录启动或打开动作。复制路径、显示详情等次要动作不能增加应用启动次数。其他条目的通用“使用次数”也必须注明统计对象，不能与应用启动次数混用。

### R2. 计数、展示和排序读取相同的行为事实

- 统计对象由来源和稳定项目身份共同确定。重建后的展示 ID、来源别名和动作入口不能创建第二份计数。
- 分开保存累计有效使用、近期有效使用、真实展示、失败和明确取消。不同指标不能借用同一个字段的语义。
- 展示次数不得出现在“使用次数”里。统计窗口不同的数字必须标明窗口。
- 成功记录返回后，下一次读取立即可见新增的 1 次使用，不能等待批写定时器。
- 当前窗口的次数在 1 秒内更新。批写、缓存刷新和重启后不能倒退或重复增长。
- 正常退出时，已接纳的有效使用必须保存。已明确报告保存成功的事件在异常退出后仍可恢复且只计一次；尚未保存的状态不能伪装成保存成功。
- 统计故障不阻断原本能够完成的用户操作。故障时不能虚构持久化成功，也不能只更新某个展示面而长期留下相互矛盾的数字。

### R3. 曝光与使用学习分离

- 搜索结果发布量、用户实际看到的项目和推荐曝光是不同指标。只统计真实可见的曝光；同一展示会话里的同一项目去重，重新打开形成新会话。
- 曝光只用于评估推荐质量，不为常用资格或使用频率加分，也不刷新执行历史的时间衰减。
- 曝光抽样必须能与完整计数区分。近似数据不得标为精确次数。
- 失败和明确取消只保留诊断口径，不扣减成功使用次数或有效使用频率。本次不把“展示但未点击”直接当负反馈。推荐命中率可以继续记录，但不增加自动点击率调权。

### R4. 常用区只展示置顶和有行为证据的常用项目

采用严格常用区。自动常用候选需同时满足：近 30 天有效使用至少 5 次，发生在至少 3 个不同本地自然日，且项目仍可执行。

- 置顶是用户决定，优先展示，不受自动常用门槛限制。零使用的置顶项目标为“已固定”，不标为“常用”。
- 只曝光、刚安装、刚索引、仅使用一次的项目不获得常用资格。
- 同一天连续使用多次，不能单独证明长期习惯。跨日使用是准入证据，不限制真实次数累计。
- 上方宫格最多 6 项，按置顶优先、合格常用排序。候选不足不拿探索内容补满。
- 没有合格项目且没有可进入宫格的置顶时，推荐列表存在便保留“此刻常用”标题，并展示学习中与“固定到推荐”的轻量提示。提示不是推荐条目，不占用焦点或数字快捷键；有常用或固定宫格项目时自动移除。冷启动内容仍在下方建议列表展示，不显示虚构的使用次数。
- 文件和文件夹即使满足常用条件，也留在列表。置顶溢出和总展示预算沿用既有操作边界，不删除置顶状态。
- 资格必须单独判定，不能依据某项从哪个召回通道进入、也不能仅依据 `frequent` 标签。

上方沿用“此刻常用”，下方暂保留“最近案例”；本次不顺带改名。

### R5. 行为评分有边界，时间偏好不能独立制造习惯

常用排序以持续的真实使用为主，近期使用和最近执行体现变化，时间偏好只微调已经有使用证据的项目。

| 信号 | 建议规则 |
|---|---|
| 持续与近期使用 | 分别观察近 30 天和近 7 天。频率增长有上界，避免历史累计永久压制新习惯。 |
| 行为衰减 | 按真实事件或日级统计的发生时间计算。不能用最近一次事件把全部历史重新变新。 |
| 最近执行 | 只由有效执行更新；展示、刷新和取消不能让它变新。 |
| 时间偏好 | 近 30 天至少 10 次有效使用、覆盖至少 3 个自然日才可加分。低于门槛不加时间分；达到门槛后仍随证据量和历史年龄调整。 |
| 分数范围 | 自动行为排序分数统一表达为 0～100。时间贡献最多占 20 分，不能靠超过范围的星期因子绕过预算。 |
| 插件自报优先级 | 只能微调建议列表，贡献最多 5 分。不能取得常用资格、置顶位置或跨区抢占名额。 |
| 缺失信号 | 标为未知，不编造历史；不能因为缺少其他信号，就把仅有的一项重新放大为满分。 |

搜索与空态推荐共用身份、执行事实和行为衰减口径，但不强行使用相同总分公式。输入搜索中，明确文字匹配继续优先；常用行为不能把无关项目推到准确匹配之前。

时间模型的公开 SDK 已存在。修正语义必须评估已有插件调用者，明确公开 API 的版本边界，不能只改宿主而保留另一套失真的 SDK 算法。

### R6. 上下文和探索在建议区竞争

- 建议列表继续接收近期使用、当前上下文、插件、新装应用、新文件和冷启动候选；所有来源按同一宿主规则竞争。
- 冷启动指没有可用的有效使用历史。已经使用过、但尚未达到常用门槛的用户不属于冷启动，不能因此解除探索名额限制。
- 当前剪贴板或选择产生的明确动作可以优先于一般建议，但不能挤掉常用区或用户固定项。
- 非冷启动时，建议列表中未使用的新装或新文件探索条目合计最多 1 项。冷启动时可以用可执行的候选补足现有总展示预算，但不得冒充常用。
- 新装和新文件探索不靠无界加分压过成熟习惯。沿用现有 7 天新鲜度范围；首次有效使用后取消未使用探索加成，进入近期使用或后续常用判定。
- 应用更新、重扫旧目录和重新索引不能伪装成新安装或新文件。保留既有安装时间与首次索引的判定约束。
- 被卸载、删除、失去权限或不能重建的项目及时退出推荐。索引过程中不能因为提交频繁而持续洗牌。

### R7. 执行后的推荐更新及时，但不打断操作

- 成功使用之后，下一次打开 CoreBox 或主动刷新时，第一份推荐结果包含最新次数、最近使用和资格变化。
- 不能只清缓存再读回旧数据库，也不能等推荐缓存自然过期才生效。
- 缓存命中、后台刷新和重新启动，不能把新行为覆盖成旧状态。在失效前开始的计算不能重新发布已经过期的结果。
- 当前可见项目的次数可以更新，但不能在用户选择、预览或按键时突然重排。顺序变化在下一次打开或主动刷新时应用，焦点不得漂移。
- 沿用现有首屏预算。缓存和统计修正不能新增等待索引结束、等待整库统计或每次打开全库重算的前置条件。

### R8. 所有现有入口和来源都使用同一规则

- CoreBox 搜索、推荐、动作面板、应用详情与受支持的 SDK 入口，使用同一动作身份和计数口径。不依赖是否携带搜索会话来决定要不要计数。
- 平台文件来源别名必须归于同一个逻辑项目。插件推荐条目的身份能对应到实际执行条目，不能只支持水合而没有执行写入。
- 复用既有来源注册表。新来源通过来源自身声明身份与能力，不能在重建器里追加来源特例。
- 只采集 Tuff 内可观测的行为。不新增系统级应用启动监听，也不追踪用户在其他应用中的操作。

### R9. 历史统计和推荐理由可信

- 不清空历史次数、不重建成零、不修改用户置顶，不用曝光推算执行次数。
- 有明确身份和口径的旧数据保留。累计次数保留，但新的时间习惯和跨日资格只使用有可靠时间证据的数据。
- 旧数据不能确定成功边界、自然日或来源归属时，保留事实并标记证据不足。不能根据总次数伪造每天的使用分布。
- 原始日志受保留规则影响，不能仅凭幸存日志把累计次数下调。升级重复执行不得重复加计。
- “常用”“最近使用”“此时常用”“已固定”“新安装”各自需要对应证据。缺失证据时不显示理由，不能用另一类理由顶替。
- 沿用隐私、保留和删除设置。本地使用事实不上传，评分解释不包含剪贴板原文、文件内容或窗口标题。

## 5. 验收标准

以下是开发完成后的验收条件。评分对照使用隔离、可重复的行为样本；入口和展示必须在真实宿主中验证，不能仅凭模拟回调宣称通过。

| 编号 | 对应规则 | 可观察结果 |
|---|---|---|
| AC1 | R1、R8 | 在应用、文件、插件、剪贴板和内置入口各完成一次主要动作，对应有效使用恰好增加 1。失败、取消、预览、后台刷新和次要应用动作不增加启动次数。 |
| AC2 | R1、R2、R8 | 同一动作经过重建、别名和多次通知仍只累计一次；用户第二次主动成功执行累计到 2。插件“不激活但执行成功”的动作不会被误判为失败。 |

| AC4 | R3 | 项目展示 1,000 次但没有有效使用，使用次数为 0，不能进入常用区；旧执行项目只被展示一次，其执行衰减分不增长。 |
