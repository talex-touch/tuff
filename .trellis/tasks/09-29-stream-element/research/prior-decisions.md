## Decisions and rejected designs, by theme

### 1. Streaming Markdown rendering architecture (`TxStreamMarkdown`)

- **Comparison-driven incremental parsing, not a "block is closed" assumption.** Markdown allows later input to rewrite earlier semantics (setext headings, list continuation lines, reference-style link definitions, table separator rows), so the design explicitly rejects "assume prior blocks are stable" in favor of: full re-lex every delta (`marked` lexer, <1ms at 5k chars) → longest strict-equal prefix of `token.raw` is the stable set → per-block HTML cache hit for the prefix → only the changed suffix re-parses and re-sanitizes. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:15-24`.
- **DOM identity is the acceptance bar, not just "looks right."** Stable blocks keep the same `block.id` across renders so Vue's patch skips them and the DOM node reference is provably unchanged — this is asserted by identity comparison in tests, not by visual inspection. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:27-28`, acceptance criterion at `.trellis/tasks/08-05-tuffex-ai-stream-markdown/prd.md:47`.
- **Code highlighter: shiki, not a reused CodeMirror instance.** Rejected reusing the existing `code-editor` (CodeMirror) integration because "CodeMirror is an editor runtime (a persistent `EditorState`/`EditorView` instance) — using it for display-level highlighting is running behind an editor just to get a paint." shiki produces static HTML compatible with the `v-html` pipeline instead. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:9`.
- **mermaid/shiki are `dependencies` + dynamic import, not `optionalPeerDependencies`.** Rejected making them optional peers because both real consumers (core-app, nexus docs) need them; dynamic import keeps the initial chunk cost at zero regardless. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:10`.
- **mermaid zoom uses a bespoke overlay, not the existing `image-gallery` lightbox.** Rejected reuse because `image-gallery` targets `<img>` elements specifically; mermaid emits inline SVG, so a lightweight custom overlay reusing `--tx-overlay-*` tokens was built instead. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:11`.
- **Streaming cursor is pure CSS**, gated on an `is-streaming` class and targeting only the last content element of the last block; a separate block-level cursor line is used when the tail block is a fenced block, to avoid polluting `pre` text. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:37-40`.
- **Reveal animation only plays once per new block id**, never replays on a tail block's repeated delta updates, and is fully suppressed under `prefers-reduced-motion: reduce`. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:42-46`.
- **Renderer registration is instance-level (`renderers` prop), not global.** The design explicitly cites the "Pencil lesson" (cross-instance pollution from global registration) as the reason a fence-language-to-block-component map is passed per-instance rather than registered globally. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:63`.
- **Performance budget and an explicit, deferred fallback path.** Budget: <4ms/frame main-thread cost at 20ms/delta injection for a 5k-char/10-block document. If exceeded, the documented fallback is "skip re-lexing the stable prefix" (only lex the character offset since the last stable boundary) — but this optimization is deliberately **not implemented in v1** ("high complexity, high correctness risk; only enable if the budget is actually exceeded"). `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:82-86`.
- **`ai-elements-vue` dependency removed as dead weight.** It sat in tuffex `dependencies` with zero source references and was removed as part of this task. `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:107`.

### 2. Message parts model — what gets added to the shared vocabulary and what deliberately does not

- **`AiSourcesPart` was added to the `AiMessagePart` union; `TxToolConfirmation`, `TxSuggestionChips`, and `TxContextIndicator` were deliberately kept *out* of parts.** Rationale recorded directly: "Confirmation/Suggestion/Context are session-layer UI, not parts." Only Sources graduated to a part type because `TxAiMessage` needs to dispatch-render it inline with other message content; the other three are addressed by the consuming session layer, not by the message-parts renderer. `.trellis/tasks/08-05-tuffex-ai-elements-port/design.md:10`.
- **`TxChainOfThought` is an independent implementation, not a composition of `TxTimeline`.** Timeline only offers a title/icon/colour face with no streaming body, state machine, or collapse; the chain-of-thought component borrows Timeline's vertical-line visual language but is built standalone. `.trellis/tasks/08-05-tuffex-ai-elements-port/design.md:9`.
- **`TxToolConfirmation` renders inline in the conversation flow, never as a modal.** Rationale: "tool execution is part of the conversation's narrative; a modal would interrupt streaming reading." `.trellis/tasks/08-05-tuffex-ai-elements-port/design.md:11`.
- **Memory/persistence policy for a "remember" checkbox is explicitly out of component scope.** The component only reports intent via `approve`/`deny` events carrying a `remember: boolean`; where that gets persisted is left to the session layer consuming the event. `.trellis/tasks/08-05-tuffex-ai-elements-port/design.md:12`, prd constraint at `.trellis/tasks/08-05-tuffex-ai-elements-port/prd.md:14` (`TxContextIndicator`, superseded in the shipped tree by `TxContextCards`/`context-cards` per Topic 2 research — the P0 catalogue in this PRD predates final naming).

### 3. `TxConversationStream` virtualization — data ownership and loader contract

- **Loader signature `{ items, hasMore }` was proposed in the PRD and explicitly rejected in design.** The PRD drafted `loadOlder?: () => Promise<{ items: T[], hasMore: boolean }>` (`.trellis/tasks/08-05-tuffex-ai-conversation-stream/prd.md:31`). Design overturned it: "returning `items` means the component manages data on the consumer's behalf, which violates [full consumer ownership]" — the accepted signature is `loadOlder?: () => Promise<{ hasMore: boolean }>`, and the **consumer** unshifts old messages into its own `items` array before the promise resolves. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:11`.
- **The component is fully controlled; it never copies `items` into internal state.** Rationale: an internal copy would create a second data source that would fight the (then-unlanded) R2 conversation transport; keeping the component's anchoring logic agnostic to *any* prepend, regardless of trigger source, was preferred. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:10`.
- **better-scroll (transform-based scroll takeover) was rejected in favor of native scroll + IntersectionObserver sentinel + manual scroll anchoring.** Reasons given: better-scroll's transform-based scroll fights an absolutely-positioned virtual window, and "pull down and release" is not the desktop-native gesture for loading older history anyway; an IO sentinel prefetching 200px early reads as "history is already there by the time you've scrolled up," closer to ChatGPT/iMessage. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:9`. This directly resolves "parent task open decision 1" from `.trellis/tasks/08-05-tuffex-ai-suite/prd.md:78`.
- **The last item is never virtualized — it is the permanent "live zone."** This holds regardless of whether the item is actually streaming, specifically to avoid "moving between the virtual and live regions when streaming starts/stops," which the design calls out as its own source of jank. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:24-25`.
- **Height cache keys are item keys, not array indices**, precisely so a prepend does not invalidate previously-measured heights. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:30`.
- **Prepend viewport anchoring**: record the anchor key (first visible item) and its pixel offset from the viewport top *before* the prepend; after DOM update, `scrollTop` is recomputed from the anchor key's new offset minus the recorded viewport offset; `overflow-anchor: none` is set explicitly to disable the browser's own native scroll anchoring, which would otherwise double-compensate. `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:46-54`.
- **A documented `vue-tsc`/expose-typing gotcha**, matching a pattern already known elsewhere in this codebase: "the public instance proxy unwraps exposed refs; `vue-tsc`'s expose surface is the unwrapped type. A hand-written `*Instance` interface that declares a `Ref` lies to the consumer — caught by a drift-contract test in practice." `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:84-85`.
- **Known, accepted boundaries** (i.e., non-goals rather than bugs): container-resize invalidates the whole height cache and only "ripples" back into correctness progressively rather than a synchronous full re-layout; `scrollToIndex` is not pixel-perfect and converges only as real measurements land; a loader firing repeatedly when content doesn't fill the viewport is mitigated by "auto-load once, then require a user scroll gesture before loading again." `.trellis/tasks/08-05-tuffex-ai-conversation-stream/design.md:96-99`.

### 4. HomePage integration (`08-05-home-chat-tuffex-ai-fusion`) — what real-world wiring rejected

- **`TxAiMessage` was evaluated and rejected for the homepage.** Verbatim rationale: "`TxAiMessage` is a 'card + role avatar' visual language, which directly conflicts with shell v2's flat reply style (no padding, no card)." The `item` slot of `TxConversationStream` instead carries HomePage's own hand-written bubble/flat-text markup, with only the *content renderer* (`TxStreamMarkdown`) substituted in for the assistant's text. `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:9`.
- **`loadOlder` was deliberately not wired in this round** because the (at-the-time unlanded) conversation transport returns the entire conversation in one call with no pagination; "no top zone" is treated as satisfying the PRD's "show 'no more history' with no jank" intent by construction, not by fetching. `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:10`; underlying transport shape confirmed at the top of the same file (`08-04 R2 已在工作树落形但未提交 ... conversation transport（整会话粒度，get 全量返回消息，无分页）`), `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:3`.
- **`TxChatComposer` was evaluated and rejected as a full replacement for HomePage's hand-rolled composer**, because the existing composer already encodes the shell design language, focus-retention-on-first-send, and IME-composition guards, and "the cost of realigning by swapping components is higher than the benefit." Paste/drop attachment logic was reimplemented locally in HomePage instead, matching `TxChatComposer`'s semantics (debounced drag counter, file extraction) without adopting the component itself. `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:11`.
- **Attachments are memory-only by explicit construction, not by oversight.** `ConversationMessage.attachments` (typed from `@talex-touch/tuffex/ai-elements`) is excluded from both `toProviderMessages()` (so degradation is structural, not a runtime check) and `toSaveRequest()` (an explicit field whitelist, so attachments are silently dropped on persist) — "attachments disappear after reload; accepted for this round and reflected in the PRD's degradation-notice requirement." `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:12`.
- **Token bridging is one-directional and scoped**: `.HomePage` maps `--tx-*` variables to `--shell-*` values in HomePage's own `<style>` block; tuffex source is never touched. Two token families are declared explicitly independent: the colour bridge (shell owns colour) and tuffex's own `theme="auto"` root-detection for structural theming of syntax highlighting/mermaid — "each layer manages its own thing: tokens manage the palette, `auto` manages the highlighter/chart theme family." `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:74`.
- **Full old→new scroll-responsibility handoff table** (stick-to-bottom, streaming-follow, "return to bottom," composer-height-driven padding, floating pill offset) is recorded explicitly rather than left implicit, because HomePage's hand-written scroll stack (`streamRef`, `handleStreamScroll`, `stickToBottom` flag, `STICK_TO_BOTTOM_THRESHOLD`, content-length watcher) is deleted wholesale in favor of `TxConversationStream`'s built-ins. `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/design.md:37-45`.
- Explicitly out of scope for this task, matching the parent's non-goals: real tool-loop triggering (`--no-tools` stays), and any multimodal payload to the provider. `.trellis/tasks/08-05-home-chat-tuffex-ai-fusion/prd.md:57`, `.trellis/tasks/08-05-tuffex-ai-suite/prd.md:71-73`.

### 5. Message rendering in true stream order (`08-07-chat-stream-order-render`)

- **Flattening every reasoning/tool-call into one `TxChainOfThought` block was the bug, not a feature to extend.** Root cause: `toChainSteps()` collapsed *all* reasoning and tool-call parts of an entire turn into one array, rendered as a single chain block, with text explicitly excluded and rendered separately as one final concatenated blob — "no matter how many actual 'think → tool → think' rounds the model went through, the UI always renders as one think block → all tools → one blob of text." `.trellis/tasks/08-07-chat-stream-order-render/prd.md:9-13`.
- **The fix segments messages into ordered `reasoning | tool | text` units, one `TxChainOfThought` per reasoning span** (not one shared block with a count), keeping the true arrival order already present in `parts` (`useHomeConversation.ts`already pushes parts in arrival order — the flattening was purely a render-layer problem). `.trellis/tasks/08-07-chat-stream-order-render/design.md:16` (data-flow note), segmentation contract at `.trellis/tasks/08-07-chat-stream-order-render/design.md:18-31`.
- **Plan escalated mid-task (2026-08-08) to also segment the text itself in place ("Plan C").** Originally only reasoning/tool were to be pulled out of the flattened block; the PRD's R8 upgrade requires that when a turn goes "text → reasoning → text," the second reasoning block lands *between* the two text segments rather than all text being pushed above both reasoning blocks. `.trellis/tasks/08-07-chat-stream-order-render/prd.md:26`.
- **A same-content dual-render trap was identified and guarded against.** Once text renders from segments, `message.content` (full concatenation) and the text-part segments contain identical content in parts mode; rendering both would show the answer twice. The guard branches on `!message.parts` (whether the turn ever entered parts mode at all), specifically *not* on segment count — branching on count would double-render a turn whose parts are "all tool calls, no text." `.trellis/tasks/08-07-chat-stream-order-render/design.md:62`.
- **Branch-order is a hard constraint, not a style choice**: the text branch must be checked before the widget/tool branch in the template, because the widget branch's condition reads `segment.part`, which text segments don't have — reversed order throws `formSpecOf(undefined)` at runtime. `.trellis/tasks/08-07-chat-stream-order-render/design.md:60`.
- **"Only the tail segment is live" reconfirmed at the segment level**: a text segment's `streaming` flag is true only when the turn is streaming **and** it is the last part in the array — "otherwise earlier segments would permanently stay in the streaming-reveal style." `.trellis/tasks/08-07-chat-stream-order-render/design.md:40`. (This is the fourth independent instance of the "only the tail is live" idiom found across this codebase, alongside `TxAiMessage.isPartStreaming`, `TxReasoningDisclosure`/`TxChainOfThought`'s auto-scroll-and-mask, and `TxStreamMarkdown`'s own tail-block handling — see `research/ai-suite-building-blocks.md` and `research/existing-streaming-components.md`.)
- **Persistence truncation policy changed because the render source changed.** `toStoredParts` previously truncated `text` parts to 8KB while `content` stored the full string; once rendering moved to consume parts directly, that truncation would visibly clip long answers on reload. Fix: `text`-type parts are no longer truncated; reasoning and tool payloads (`output`/`logs`/`input`/`error`) keep their caps. Accepted cost: the answer text now exists twice in storage (`content` plus the text part), justified because it stays the same order of magnitude as the answer itself and `content` is still needed for plain-text turns and the copy button. `.trellis/tasks/08-07-chat-stream-order-render/design.md:64-68`.
- **A one-character API change to `TxChainOfThought` was made in tuffex to serve this caller**: the step-count badge changed from always rendering `{{ steps.length }}` to `v-if="steps.length > 1"`, justified as "a general improvement (a count of 1 is never informative in any context)" and deliberately not exposed as a new prop, since `TxChainOfThought`'s only consumer is HomePage. `.trellis/tasks/08-07-chat-stream-order-render/design.md:79-83`. This is a concrete precedent for how narrowly-scoped a tuffex change can be made when the component has exactly one call site.
- **Collapse-state key granularity dropped from message to segment.** `chainOpen` used to be keyed by `message.id`; once one message can have multiple reasoning blocks, the key must be `segment.id` (reasoning segments keyed by array index, tool segments by `part.id`) to keep each block's expand/collapse state independent and stable across streaming re-renders. `.trellis/tasks/08-07-chat-stream-order-render/design.md:85-89`.
- Helpers explicitly deleted rather than generalized: `soloToolOf`, `showChain`, and the index-based `shouldUseChainView` — all existed only to answer "is this worth collapsing/is this a special single case," a question that no longer applies once every reasoning span is its own always-rendered block. `.trellis/tasks/08-07-chat-stream-order-render/design.md:45`, `.trellis/tasks/08-07-chat-stream-order-render/design.md:70-75`.

### 6. Pipeline fixes (`08-06-home-chat-pipeline-fixes`, parent-level only)

- **The message pile-up bug's root cause chain is a direct warning for any future virtual-list-hosted streaming element**: per-conversation counter-based message ids (`user-1`, `assistant-2`) collided across threads inside one keep-alive'd `TxConversationStream` instance whose height cache was never pruned, and restoring a conversation reset `messageSeq = restored.length`, which re-minted already-used ids after message drops — wrong/stale heights led to 96px-estimate offsets and visually overlapping rows. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:7-12`. This is codified as a binding rule in the spec (see Binding Rules section below, "Virtual List Keys and Height Caches").
- **`showChain()`'s single-step visibility rule was too strict**: it required `status === 'streaming'` for single-step reasoning trails to render at all, so a settled (non-streaming) single-thinking-step turn's trail vanished on completion even though the underlying reasoning data was intact and persisted. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:13`. (Superseded entirely once `08-07-chat-stream-order-render` removed `showChain` altogether — see above.)
- **Compaction events were silently dropped, not merely unhandled**: `pi` emits `compaction_start`/`compaction_end` JSON lines on stdout, and `parsePiCliLine` discarded them, so the app replayed full, uncapped history on every process spawn instead of adapting to a compacted context window. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:19`.
- **Web search was never implemented, not merely disabled**: no gateway tool exists, and the installed `pi` 0.84.0 build has no built-in web search (verified by inspecting its dist directly, not inferred). `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:16`. This child was still blocked on a backend-provider decision as of the status table. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:56`.
- **Send-motion polish diagnosed four concrete motion defects** rather than a vague "not smooth enough" complaint: a ~196ms artificial pre-flight queue delay, per-frame `blur()` re-rasterization cost, `setTimeout`-based beat drift, and restarted ease-out follower tweens mid-stream. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:20-21`.
- Ordering dependency recorded explicitly: land the id/cache/virtualization fix *before* send-motion polish, "since motion polish is easiest to judge on a correct layout," even though the two children don't share files. `.trellis/tasks/08-06-home-chat-pipeline-fixes/prd.md:33-35`.

### 7. Stream-markdown polish (`08-09-stream-markdown-polish`) — matches the currently-shipped API

- **Every "gap" was measured by actually running `marked` on a truncated stream**, not by inspection or assumption — the PRD opens with a table of literal broken outputs (`**bold` renders as literal `**bold`, `$E=mc^2$` renders as literal because "no KaTeX anywhere in the repo," a half-arrived table row renders as "a sheet of pipe characters"). `.trellis/tasks/08-09-stream-markdown-polish/prd.md:7-15`.
- **Inline-markup completion only ever speculates at the very tail of the document.** An unclosed `*` mid-document is treated as a deliberate literal (`2 * 3 * 4`) and never rewritten; only the trailing, still-streaming run gets speculative closing. Fenced code blocks and inline-code contents are never touched by this pass — that remains the block-stream layer's job, and closing it early there would prematurely end a code block. Runs of more than 3 delimiter characters are treated as a divider/ASCII art, not emphasis. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:33-39` (source: `packages/tuffex/packages/components/src/stream-markdown/src/complete-inline-markup.ts`, confirmed exported from `stream-markdown/index.ts:40`).
- **KaTeX's `$`-detection is called out as the single highest-risk surface of the whole polish task, and the stated tradeoff is explicit: "would rather under-render than swallow real prose."** A missed formula is a small disappointment; treating literal text like `$5 到 $9` as a math span is a real information loss on screen. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:51-53`.
- **A real, build-only-discovered bug: importing KaTeX's CSS from inside a tuffex SFC breaks its fonts.** tuffex's *library* build rewrites relative font URLs to absolute paths (`/assets/KaTeX_*`) but does not emit any font files with them — both the tuffex dist and the consuming app's dist ended up with zero KaTeX font files, silently falling back to substitute fonts (which KaTeX's own metrics depend on, so formulas looked visibly broken). The fix — and the resulting convention — is that **the host application imports KaTeX's CSS, not tuffex**, matching KaTeX's own recommended integration; tuffex was rebuilt to purge the stale absolute references. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:56`.
- **Link/image hardening findings reversed the task's own starting assumption.** The initial premise was that new sandboxing work was needed; investigation found the real protections already existed: the main process's `will-navigate` handler already intercepts and hands off to the system browser, `validateExternalUrl` already enforces a protocol allowlist (`http/https/mailto/tel/tuff`, rejecting `file:`/`javascript:`), and DOMPurify **already strips `target` by default**, which independently closes the "open a new Electron window" attack path (the main window has no `setWindowOpenHandler` at all — only plugin windows do). The actual remaining work was defense-in-depth (`rel="noopener noreferrer"`) plus image hardening (`loading="lazy"` — explicitly framed as "a mitigation, not a perf optimization," since off-screen images literally never fetch and thus never beacon — plus `referrerpolicy="no-referrer"`, `decoding="async"`, and guaranteed non-empty `alt`). `.trellis/tasks/08-09-stream-markdown-polish/prd.md:76-86`.
- **An escaping asymmetry was found empirically, not assumed**: `marked` hands back `title` and link-text/image-`alt` already HTML-escaped, but `href` raw — so only `href` is passed through `escapeHref`; escaping the others a second time would double-escape and show the reader literal `&amp;quot;`. Both call sites carry assertions specifically to prevent a future "simplify to one path" regression. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:86`.
- **Remote-image blocking defaults to on, with state held at module scope, not component scope, and cleared per-conversation.** Rationale for module-level (not per-component) state: one conversation renders one `TxStreamMarkdown` per message, so component-level state would force the reader to re-approve the same remote host on every subsequent message. Rationale for clearing on conversation switch: "the permission is granted for one conversation; carrying it into the next thread would silently widen it without the reader's knowledge." Because the placeholder is injected as raw `v-html` (so Vue can't bind a click handler to it directly), the click-to-allow interaction is wired through a single delegated listener on `.markdown-body` that reads `data-*` attributes instead. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:88-97`.
- **This task's file list matches the shipped `stream-markdown` module almost exactly**: `complete-inline-markup.ts` (§1), `math-extension.ts` (§2, not directly cited above but referenced at `.trellis/tasks/08-09-stream-markdown-polish/prd.md:47`), `completeTable` living in the same module as the inline-markup work (§3), `harden-html.ts` (§4), and `remote-image-policy.ts` (§4b) — all of which are re-exported today from `packages/tuffex/packages/components/src/stream-markdown/index.ts:33-41` (`allowRemoteImageOnce`, `allowRemoteImagesForSession`, `isRemoteImage`, `isRemoteImageAllowed`, `resetRemoteImagePolicy`, `completeInlineMarkup`, `completeTable`, `createBlockStream`). This confirms the currently-shipped component already carries this task's polish, beyond what the original `08-05-tuffex-ai-stream-markdown` design alone would produce.
- **Table streaming was solved by synthesizing a separator row, not by hiding the table until it's complete.** Before the separator row arrives, `marked` renders the header as a plain wall of pipe characters for several seconds on a wide table; the fix synthesizes a matching separator row so the header renders as a header immediately, handling both arrival orders (header-only-so-far; data rows arriving before the separator, in which case the separator is spliced between them). Only the trailing, still-in-flight table run is touched — already-settled tables and prose above it are left alone. Copy-to-CSV was scoped as a separate, unimplemented follow-on because it requires a hover-revealed button (a component-level addition), not a styling change. `.trellis/tasks/08-09-stream-markdown-polish/prd.md:64-70`.

## Binding rules — `.trellis/spec/frontend/`

Read in full: `component-guidelines.md`, `tuffex-design-rules.md`, `tuffex-docs-sync.md`, `tuffex-text-motion.md`, plus the index at `index.md`.

### Registration / wiring chain (applies to any new `StreamElement`/`StreamText`/`StreamCode` component)

A component is "done" only once the full chain below is complete — this is stated as an explicit numbered checklist, not a suggestion:

1. Directory under `packages/tuffex/packages/components/src/<kebab-dir>/` → registered in `components.ts` → added to exactly one of the `base`/`pro`/`ai` barrels → added to Nexus taxonomy/sidebar/gallery/hub index → both `.zh.mdc` and `.en.mdc` written → a demo component → a line in `demo-registry.ts`. `.trellis/spec/frontend/tuffex-design-rules.md:322` (checklist item 8), full detail in `.trellis/spec/frontend/tuffex-docs-sync.md` (see below).
2. `packages/tuffex/packages/components/src/__tests__/suite-barrels.test.ts` mechanically asserts the union of `base/index.ts` + `pro/index.ts` + `ai/index.ts` equals `components.ts` with **no overlap** — this is CI-enforced, unlike most of the taxonomy conventions. `.trellis/spec/frontend/component-guidelines.md:430`.
3. **The docs-coverage contract is enforced only by the Nexus test suite, not by the gate scripts.** `check:mdc-fences`, `check:doc-parity`, `check:demo-registry`, and `recategorize --check` all pass on a component whose docs are entirely missing. The actual gate is `apps/nexus/test/docs/tuffex-component-docs-coverage.test.ts`, which requires, per exported slug, in both locales: a live `TuffDemoWrapper`, an `## API` H2, a `Props`/`属性` heading, and a heading spelled exactly `Best Practices` (en, case-sensitive) / `最佳实践` (zh), plus a link from that locale's hub page. Run via `pnpm -C packages/tuffex build` then `pnpm -C apps/nexus exec vitest run`. `.trellis/spec/frontend/component-guidelines.md:434`.
4. Adding a *component* to an existing suite requires: a `TAXONOMY` entry (`apps/nexus/scripts/recategorize-component-docs.py`), the matching suite barrel, `SECTION_ORDER` kept in the same order as `TAXONOMY`, links from both hub `index.{zh,en}.mdc` files under its suite (bumping that suite's Suite Overview count), and — specifically for the **ai** or **data** suites — a gallery cell, because those two gallery bands are *exhaustive* (one cell per component) while base/pro are curated. `.trellis/spec/frontend/component-guidelines.md:431`, `:438`. Since 13 of the 14 components surveyed in `research/ai-suite-building-blocks.md` live in the `ai` barrel, a new `StreamElement`/`StreamText`/`StreamCode` in that suite would need an exhaustive gallery cell, not an optional one.
5. The suite-taxonomy system is **two independent maps that are not required to align**, restated here consistent with Topic 2's finding: the barrel taxonomy (`base`/`pro`/`ai`, exactly 3, CI-enforced) and the docs-category taxonomy (7 keys: concepts/templates/base/pro/ai/data/flow, driven by frontmatter `category`, convention-only). `.trellis/spec/frontend/component-guidelines.md:422-424`.
6. **Frontmatter is not gate-checked for validity.** An unquoted `: ` inside a YAML value produces a page with `category: null`, silently dropping it into the sidebar's "misc" bucket in every suite, and none of the fence/parity/taxonomy checks catch it — the only detection method given is polling the live sidebar API for rows missing a category after adding pages. `.trellis/spec/frontend/tuffex-docs-sync.md:139`.

### Docs sync (binding on any prop/behavior change, not just new components)

- **A component's own docs plus every wrapper's docs must move together, in the same commit.** The worked failure case: `loading` was added to `TxSwitch` and `TxBlockSwitch` was rewired to it; `TxSwitch`'s own docs were fully updated but `TxBlockSwitch`'s (the wrapper) kept describing a spinner and row-dimming that no longer existed — nothing failed CI. `.trellis/spec/frontend/tuffex-docs-sync.md:9-11`.
- **Finding wrappers requires searching by import path, not by tag name**, because tags get re-aliased: `rg -l "\.\./\.\./$COMP'" packages/tuffex/packages/components/src --glob '*.vue'`. `.trellis/spec/frontend/tuffex-docs-sync.md:24-25`. This is directly relevant if `StreamText`/`StreamCode` end up wrapped by `StreamElement`, or if `TxStreamMarkdown` itself becomes a wrapper over a new `StreamText` primitive (the exact scenario Topic 4 of this research is investigating) — any prop/behavior change to the inner primitive would obligate an update to every wrapper's docs, found this way.
- **A user-visible change requires a real demo, not a props-table row.** Demo requirements: a `<Comp><Variant>Demo.vue` file following existing i18n/labels conventions, one alphabetical registry line, and a `TuffDemoWrapper` block in both locale `.mdc` files. `.trellis/spec/frontend/tuffex-docs-sync.md:72-78`.
- **Gallery cells have specific structural requirements** that a new streaming showcase cell would have to satisfy: the `<ClientOnly>` stage must be `DocsGallerySpecimen.vue` (not Nuxt's own `ClientOnly` directly) to get the replay/reset button; anything that loops, auto-advances, or scripts its own playback must live in its own component under `docs/gallery/` and (re)start inside its own `onMounted` so a reset actually restarts it (`useGalleryLoop` exists for this and already respects reduced motion); teleported content (a modal/overlay) cannot read `--docs-*` tokens (only `--tx-*` works there) and must be teleported (`position: fixed` inside `.docs-prose`'s `content-visibility: auto` otherwise lays out against the whole article, not the viewport). `.trellis/spec/frontend/tuffex-docs-sync.md:93-97`.
- **A cross-cutting infra trap for demoed streaming widgets**: in a production Nexus build, `@talex-touch/tuffex/utils` (and the auto-registered components) resolve to a *second module instance* separate from source-built components, so anything with singleton/module-level state splits across the two — e.g., a toast queue pushed from one instance never reaches a toast host mounted from the other. This is directly relevant to `TxStreamMarkdown`'s own module-level remote-image-policy state (Topic 3, §7 above): if a StreamElement showcase demo and the "real" app-mounted copy of the same primitive ever end up on opposite sides of that module split, the module-level policy singleton silently stops being shared. `.trellis/spec/frontend/tuffex-docs-sync.md:84`.
- Docs pages are hand-written prose with **no regenerating gate**, so a stale claim (a described behavior that no longer exists) never turns red by itself — the entire mechanism is manual discipline plus the blast-radius search above. `.trellis/spec/frontend/tuffex-docs-sync.md:3`.

### Motion / reduced-motion / SSR rules with direct bearing on a streaming reveal/caret design

- **Every declared transition or animation must carry a `prefers-reduced-motion: reduce` escape**, and a dropped keyframe animation must still leave the element in its *finished* frame, not merely stop animating — a fade-in that starts at `opacity: 0` and never reaches 1 under `animation: none` is a documented failure mode (worked example: `TxEmptyState`). The equally valid, smaller alternative is to declare the animation only inside `@media (prefers-reduced-motion: no-preference)`, so the reduced-motion element simply rests at its plain declared style; a style-contract test must assert whichever form was chosen. `.trellis/spec/frontend/tuffex-design-rules.md:188-198`. This is a second, independently-stated codification of the same rule Topic 1's research already found implemented inside `TxStreamMarkdown`'s reveal animation and cursor.
- **Hover must never ease colour.** `color`/`background-color`/`border-color` may never sit inside a `transition` that fires on `:hover` — only geometry/opacity/shadow may ease on hover. A state change (not a hover) may ease colour, but only by gating the transition on a temporary class added for the duration of the change, never by declaring the transition on the element itself (which would also ease every hover). `.trellis/spec/frontend/tuffex-design-rules.md:159-186`. Relevant to any citation-chip or source-chip "pop in" styling in the planned showcase if it also carries a hover state.
- **A looping/ambient effect (the kind a "thinking"/streaming caret idiom is) must run entirely on the compositor**: animate only `translate`/`scale`/`rotate`/`opacity`, keep `var()` out of `@keyframes` (per-instance parameters reach the animation through `calc()` in `animation-duration`/`animation-delay`, not through keyframe values), and a growing host under a loading effect must retract the effect (~140ms) rather than share a frame with newly-arrived content, watched via `ResizeObserver` (ignoring sub-8px reflow noise from late web fonts). `.trellis/spec/frontend/tuffex-design-rules.md:247-269`. Directly applicable to any caret/orb/shimmer idiom a `StreamText`/`StreamElement` primitive might add on top of the ones already inventoried in `research/ai-suite-building-blocks.md`.
- **A replay needs a second keyframe name, not a re-added class**: re-adding a class already present on the element does not restart a CSS animation, and forcing reflow (`void el.offsetWidth`) spends a real layout on a decorative beat; the fix is two keyframe names with identical bodies, flipped between on each replay. `.trellis/spec/frontend/tuffex-design-rules.md:230-245`. Relevant if a StreamElement/StreamText showcase needs a "replay the reveal" affordance (the kobra.systems-style demo implies a Next/Reset control, matching the gallery specimen's own replay button convention above).
- **One writer per CSS custom property.** A `:style` binding and an imperative `style.setProperty()` must never target the same custom property name, because Vue turns an `undefined` bound value into `style.setProperty(name, '')` on *every* patch, silently deleting whatever the imperative side wrote. `.trellis/spec/frontend/component-guidelines.md:157-177`. Relevant to any measurement-driven layout value (e.g., a caret position, a chip's stagger index) a StreamElement primitive might write both declaratively and imperatively.
- **SSR/no-`document` guard convention**: components with real-DOM dependencies (mermaid rendering, ResizeObserver-based measurement) must not throw when mounted without a `document`, gated behind an explicit `hasDocument()`-style guard — confirmed both as a stated constraint (`.trellis/tasks/08-05-tuffex-ai-suite/prd.md:55`: "heavy deps must be dynamic-import, must be SSR/no-`document`-safe, reusing the `hasDocument()` guard convention") and as an implemented behavior (`TxMermaidBlock`'s renderer stops at its skeleton state under `hasDocument()` — `.trellis/tasks/08-05-tuffex-ai-stream-markdown/design.md:80`).
- **`TxTextTransformer`/`TxTextMorph` is the single sanctioned engine for animating a *changing* text value** (word/character/number diff-and-morph); a second implementation of that concept is explicitly against convention: "Do not write a second one. Before adding any per-character, per-digit, or crossfade animation to a component, check whether `TxTextMorph` already expresses it." `.trellis/spec/frontend/tuffex-text-motion.md:13-14`. This is a real design-boundary question for `StreamText`: the text-morph engine's job is diffing one value into a *different* value with WAAPI; a `StreamText`'s job (per the task's own framing, word-by-word reveal of new content) is closer to progressive *appearance* of never-before-seen tail content, which is a different problem than what `TxTextMorph` solves — the engine assumes a value can *change* (including shrinking/reordering), not just grow. This overlap-or-not question is a live design question the spec does not resolve either way; it only forbids a second morph-diff engine, not a second reveal/append mechanism.
- **A morph only animates a value change on an already-mounted engine instance** — keying the component by message id and remounting it every update swaps text instead of morphing it, and Vue "stops owning the children after mount" (the engine renders the initial value once for SSR hydration, then freezes; a later Vue re-render mid-morph would wipe segments). `.trellis/spec/frontend/tuffex-text-motion.md:134-136`, `:151-152`. If any part of a StreamElement/StreamText showcase reuses `TxTextTransformer`/`TxTextMorph` (e.g., for the "follow-up chips fade up staggered" idiom, or a numeric token counter), this keying trap applies directly.
- **Virtual-list key/height-cache contract is spec-codified, not just a `TxConversationStream`-local convention**: "Item ids fed to a virtual list must be globally unique across datasets, not per-collection counters," citing the exact `08-06` pile-up bug as the regression this rule exists to prevent, plus "hosts that pad or prepend content above the transcript rely on the component's measured spacer origin — never reintroduce 'scrollTop is spacer-relative' assumptions." `.trellis/spec/frontend/component-guidelines.md:390-403`. Directly binding on any showcase that streams a `StreamElement` output inside `TxConversationStream`.
- **Ready content must not wait for reveal motion** in list/grid rendering contexts: wrapping a content-ready branch switch in `<Transition mode="out-in">` defers mounting until the old branch's animation completes, even though other parts of the UI (e.g., a footer) already reflect the new state — stated for CoreBox's result list, but the underlying principle (never gate *readiness* on an optional reveal animation) generalizes to any streamed content appearing inside a list. `.trellis/spec/frontend/component-guidelines.md:334-345`.

### Naming / structural rules

- **`Tx` prefix, `defineOptions({ name: 'Tx…' })`, `withDefaults(defineProps<Props>(), …)`, kebab-case directory** is the standard shape for a new TuffEx primitive, shown against `TxFileUploader`. `.trellis/spec/frontend/component-guidelines.md:19-35`.
- **Size vocabulary must reuse an existing union** (`xs | sm | md | lg` is the standard spelling for new components), checked via `pnpm -C packages/tuffex audit:vocab`; a single component accepting two spellings of one tier (e.g. both `small` and `sm`) is treated as a defect, not a style choice. `.trellis/spec/frontend/tuffex-design-rules.md:315-316`.
- **Status vocabulary reuses `'default' | 'error'`** unless the domain genuinely needs more states; `error` is the prop-facing name even though the underlying token is `--tx-color-danger`. `.trellis/spec/frontend/tuffex-design-rules.md:317`.
- **Every user-visible string is a prop with a documented default** — TuffEx owns no message catalog of its own. `.trellis/spec/frontend/tuffex-design-rules.md:319`.
- **New interactive UI must use semantic controls** (`button type="button"`, not `div @click`), with keyboard/focus behavior preserved. `.trellis/spec/frontend/index.md:91`, elaborated in `.trellis/spec/frontend/component-guidelines.md:357-376`.
- **Colour is `--tx-*` tokens only**, with the fallback literal existing only for hosts that load a component's CSS without `variables.scss` — never a real value in its own right. `.trellis/spec/frontend/tuffex-design-rules.md:101-107`.
- **Content text sits at 13–14px**; 16px+ is reserved for headings — a component needing 16px body content is read as a hierarchy bug, not a styling choice to accommodate. `.trellis/spec/frontend/tuffex-design-rules.md:11-19`.
- **A skeleton is the default (non-optional) loading state** for any view whose layout is known before data arrives, built from the same containers as the loaded view and reusing `TxRowSkeleton`/`TxSkeleton`/`useDeferredLoading` rather than hand-rolled placeholders. `.trellis/spec/frontend/index.md:93`, `.trellis/spec/frontend/component-guidelines.md:299-332`. If a StreamElement showcase includes a "waiting for first token" affordance, this convention — plus the already-documented `TxThinkingOrb`/`TxWorkingIndicator`/typing-dot idioms from Topic 2 — is the relevant prior art, not a fresh skeleton design.
- **The "new component checklist"** (`.trellis/spec/frontend/tuffex-design-rules.md:313-323`) additionally requires: component-local CSS custom properties per size class rather than duplicated rule blocks; screen-reader-only text via the clip pattern, never `display: none`; a `role="status" aria-live="polite"` region for any state that changes without direct user action (directly relevant to a streaming text region announcing its own updates — compare `TxTextTransformer`'s hard-coded `aria-live="polite"` root, `.trellis/spec/frontend/tuffex-text-motion.md:139`); and a stylesheet-size budget check (`pnpm -C packages/tuffex audit:size`) that a new component is expected to fit inside rather than trigger a gate bump.
