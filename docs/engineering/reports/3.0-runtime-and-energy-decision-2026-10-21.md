# 3.0.0 运行时选型与能耗目标

> 日期：2026-10-21（状态同步：2026-11-27）
> 状态：决策记录（运行时不变）+ 分期实施中（Phase 0 局部实机采证，Phase 1/2/3 代码切片已合入，Phase 0 Metric 2 与 `v2.4.15-beta.15` 打包空闲/长稳验收门禁仍开放）
> 触发：讨论「3.0.0 换 CEF / Tauri / 原生」，首要目标被确定为**能耗与常驻内存**

---

## 1. 结论

**3.0.0 不更换应用运行时**：继续用 Electron 承载窗口与渲染层，把 3.0 定义成「内核进程化 + 空闲预算 + 渲染层能耗」三件事。CEF、Tauri、原生三条路线的问题不是"能不能做"，而是**它们换掉的不是当前的痛点，却要重写最贵的资产**。

判定依据按投入产出排序：

| 事实 | 数值（2026-10-21 本仓库） | 对选型的含义 |
|---|---|---|
| 主进程规模 | 966 个 TS 文件、约 35.0 万行（非测试） | 任何换宿主方案都是主进程全量重写 |
| Electron 耦合面 | 164 个文件 `import 'electron'`；`session.` 1,308、`BrowserWindow` 259、`Tray` 211、`WebContentsView` 96、`powerMonitor` 82、`screen` 40、`globalShortcut` 12 | 耦合集中在 shell（窗口/托盘/快捷键）与网络会话，恰恰是 Electron 替我们兜住的部分 |
| 原生模块 | `packages/tuff-native` 21,418 行 Rust/ObjC，全部 N-API | 离开 Node（Tauri）就无处挂载，必须重做成宿主侧；见 [`native-rust-runtime-migration-prd`](../../plan-prd/03-features/native-rust-runtime-migration-prd.md) §2 的 TCC/签名结论 |
| 验证资产 | 1,679 个测试文件 + 一整套 CDP 探针（`apps/core-app/scripts/coreapp-*`） | 换壳等于重做验收体系；CDP 是当前唯一能自动验收打包界面的通道 |
| 目标平台 | macOS arm64/x64、Windows nsis、Linux | 原生路线要么三份 UI，要么砍两平台；Tauri 的 Linux 侧是 WebKitGTK，同一份 CSS 三个引擎 |
| 现场内存 | 开发态实例 8 个 Electron 进程共 1,016 MB，其中**主进程 414 MB**、GPU/渲染 248+121 MB | 最大单块就是主进程，那是内核问题，不是壳的问题 |

## 2. 三条候选路线为什么不选

- **CEF**：把 Electron 已经提供的「Chromium + Node + 三平台打包 + 自动更新 + 签名公证」全部退回自建，Chromium 合流负担一点不减。仓库内的 [`electron-browser-feasibility-survey-2026-10-17`](./electron-browser-feasibility-survey-2026-10-17.md) 已定界：通用浏览器才需要 CEF / Chromium fork（Brave 从 Muon 推翻重建就是这样付过学费），垂直工作台用 `WebContentsView` 就是正解，而内嵌浏览器工作台已经交付。收益≈0，成本≈主进程全量。
- **Tauri 2**：渲染层可复用，但主进程 35 万行要用 Rust 重写，或挂 sidecar Node —— 变成两套运行时，常驻内存反而更高；21.4k 行 N-API 原生模块在 WKWebView 进程里没有 Node 可挂；`session`/代理/快照冻结/CDP 探针全部重做；Linux 侧 WebKitGTK 让 tuffex 的视觉验收多一条通道。它能省的是安装包里的 Chromium，而当前抱怨的是运行时能耗。
- **原生（Tern 路线）**：Tern 可行有三个前提 —— macOS-only、产品文本中心（终端/编辑器）、自建渲染引擎（`stencil_ui`/`stencil_css`/`stencil_gfx` 一套自研 DOM/CSS/Metal 合成，外加 `tern shot/record/trace` 自建工具链）。Tuff 的护城河是「三平台 + 集成面广 + JS 插件 + 内嵌浏览器」，原生路线把这四条一起削掉，成本以年计。

复核记录：`/Applications/Tern.app` 只有 `Contents/MacOS/tern`（145 MB，arm64），无 `Frameworks`，`otool -L` 仅系统框架（AppKit/WebKit/JavaScriptCore/Metal/CoreText/ScreenCaptureKit/CoreData/CloudKit/ServiceManagement），无 `libswiftCore`；`strings` 中 30 处 `electron` 全部来自文件类型图标表（`dev-electron`、`md-electron_framework`），`TAURI_INTERNALS` 为 0；Info.plist 0.9.5、最低 macOS 13。即：不是 Electron，不是 Tauri，是 Rust + AppKit 外壳 + 自研 UI 引擎 + WKWebView 只承载网页 pane。

## 3. 3.0.0 的定义

三件事，按收益顺序：

### Phase 0 — 基线（先量后改）

在 mac-work 上装当前正式包，采三组数：冷启动到 CoreBox 可交互、空闲 10 分钟能耗（`powermetrics --samplers tasks` 与 Activity Monitor 的 Energy Impact 各取一次）、按进程常驻内存（`app.getAppMetrics()` 探针，复用 `observability` 模块）。没有基线不开工。

> **2026-11-23 Phase 0 采集工具与静态基线同步（PR `#2259`，`d317be0cd`）**：可复现三指标采集探针 `apps/core-app/scripts/coreapp-energy-baseline-probe.mjs`（含 18 项单测 `coreapp-energy-baseline-probe.test.ts`、`--dryRun`、`--attachOnly`、fail-closed 活实例守卫、`powermetrics --samplers tasks` 解析与 `app.getAppMetrics()`/`ps` 按角色聚合）已合入主线。`--staticAudit` 扫描 `apps/core-app/src`（3,010 文件）与 `packages/tuffex`（1,514 文件）实测当前运行时（非测试）锚点计数：`setInterval` **44** 处（39 core-app / 5 tuffex；含测试共 55）、`powerMonitor` **52** 处（51 core-app / 1 tuffex；含测试共 78）、`requestAnimationFrame` **140** 处（27 core-app / 113 tuffex；含测试共 153）。**注意**：mac-work 正式包实机冷启动、10 分钟空闲能耗与按进程常驻内存实测仍处于 pending 状态，未完成前不启动 Phase 1。

#### 2026-11-23 实机打包采证（`/Applications/Tuff.app` `v2.4.15-beta.13`, `darwin/arm64`, commit `645e8a01a`）

- **Metric 1（冷启动到 CoreBox 可交互）**：**`3,429 ms`**（`readinessMode: visible-interactive`，隔离 profile，PR `#2275` 修复打包隔离启动与 CDP 就绪判定后实测）。
- **Metric 3（空闲 10 分钟 / `600s`，`121` 次 `app.getAppMetrics()` 每 5s 采样，共 5 个进程）**：
  - **总计**：RSS min `573.47 MiB` / **median `633.58 MiB`** / p95 `915.97 MiB` / max `1,093.59 MiB`；总 CPU median `3.46%`（p95 `4.27%` / max `16.79%`）。
  - **按角色拆解**：
    - `Browser`（1 进程）：RSS min `154.53 MiB` / **median `182.72 MiB`** / p95 `290.22 MiB` / **max `454.39 MiB`**；CPU median `0.04%` / max `6.44%`（启动与索引峰值显著，验证 Phase 1 迁入 `utilityProcess` 的收益）。
    - `GPU`（1 进程）：RSS median `72.91 MiB`（max `96.44 MiB`）；**空闲 CPU median `1.88%`**（min `1.58%`）。
    - `Renderer`（2 进程）：RSS min `303.00 MiB` / **median `337.30 MiB`** / p95 `508.98 MiB` / max `740.86 MiB`；**空闲 CPU median `1.51%`**（min `1.13%`）——`GPU + Renderer` 合计占 10 分钟空闲态 CPU 的 ~98%（`3.39% / 3.46%`），为 Phase 2/3 空闲预算与渲染停帧提供直接量化依据。
    - `Utility`（1 进程）：RSS median `38.73 MiB`，CPU median `0.00%`。
- **Metric 2（空闲能耗，未收口）**：`powermetrics --samplers tasks` 需 root 权限，本次状态为 `requires-sudo`（探针已输出复现命令 `sudo powermetrics --samplers tasks -i 5000 -n 120 > .../powermetrics-tasks.txt`）；Activity Monitor Energy Impact 为 `pending-manual-import`。因此严格口径下 **`baselineClaimable: false`**（`liveMeasurementsCaptured: true`），后续补齐 sudo `powermetrics` 与 Activity Monitor 手工导入采样后方可合拢 Phase 0 完整门禁。

### Phase 1 — 内核进程化

把文件/应用索引、搜索、正文与向量索引、扫描与回填搬进**同一个 bundle 内的 `utilityProcess`**（不是独立 CLI：同一签名身份才能继承 TCC，见 native PRD §2）。主进程只做路由与窗口。收益：主进程最大的一块内存搬走；扫描/回填不再与 UI 抢主线程；崩溃隔离。

> **2026-11-23 Wave 7 进展（PR `#2279` `d73e7cb1c` + PR `#2280` `5f3439b6f`）**：已完成 Phase 1 Slice 1（同包体 `utilityProcess` 搜索与索引内核宿主基础，产物 `out/main/search-kernel-process.js` 零 Electron GUI 导入）与 Slice 2（`SearchIndexWorkerClient` / `SearchIndexReadWorkerClient` 桥接至共享 `SearchKernelClient`，通过 `TUFF_SEARCH_KERNEL_UTILITY_PROCESS=1` 可选启用，默认仍保持 `worker_threads`）。纯 Node 跨进程 RSS 隔离基准（`apps/core-app/scripts/coreapp-search-kernel-rss-benchmark.mjs`，`darwin-arm64`，5,000 条目 + 500×384 维向量 + 30 次 FTS + 10 次语义检索，`parityVerified: true`）实测：主进程峰值 RSS 由 `260.45 MiB` 降至 `73.09 MiB`（**`-187.36 MiB` / `-71.94%`**），主进程负载 RSS 增量由 `+205.13 MiB` 降至 `+17.89 MiB`（**`-91.28%`**），无查询延迟回退。**门禁与范围说明**：上述 Slice 1/2 是在 Phase 0 Metric 1（冷启动 `3,429 ms`）与 Metric 3（10 分钟空闲按进程 RSS/CPU，`liveMeasurementsCaptured: true`）完成实机采证后，仅针对 `TUFF_SEARCH_KERNEL_UTILITY_PROCESS=1` 可选开关执行的范围豁免（默认路径仍保持 `worker_threads` 不变）；Phase 0 Metric 2（`sudo powermetrics` 与 Activity Monitor 手工导入，`baselineClaimable: false`）仍处于未收口状态，且上述 RSS 数值为纯 Node 跨进程基准——在补齐 Metric 2 实测并完成后续打包版本（`v2.4.15-beta.15`+，覆盖 Phase 1/2/3 合流构建）Electron `TUFF_SEARCH_KERNEL_UTILITY_PROCESS=1` soak 验证前，不切换默认路径，也不宣称 Phase 0 或 Phase 1 门禁已关闭。

### Phase 2 — 空闲预算

审计 15 个 `setInterval` 使用点与 82 处 `powerMonitor`，建立 idle 状态机：CoreBox 关闭、窗口隐藏、系统空闲时，索引/向量/OCR/AI 全部降到 0 Hz；托盘常驻只保留事件驱动。

> **2026-11-26 进展（PR `#2322`，`be7b69729`）**：已落地主进程 `IdleBudgetCoordinator`（`apps/core-app/src/main/service/idle-budget-coordinator.ts`，含 `idle-budget-coordinator.test.ts` 单测套件），建立显式三态状态机（`active` / `background-hidden` / `system-suspended`，默认 `15s` 隐藏宽限期），接入 `powerMonitor`（`suspend`/`resume`/`lock-screen`/`unlock-screen`）、窗口可见性与 `PollingService` 全局压力控制，在后台隐藏或系统休眠/锁屏时暂停空闲轮询（覆盖 `analytics-module`/`system-sampler`、`file-provider-worker-status-service`、`file-provider-content-capacity-service`、`download-center`/`error-logger`、`network-module`、`ocr-service` 与 `perf-monitor` 严重卡顿循环），恢复活跃时立即解除并切回正常节奏。**门禁说明**：当前为代码与单测验证；Phase 0 Metric 2（`sudo powermetrics` + Activity Monitor 手工导入，`baselineClaimable: false`）及 `v2.4.15-beta.15` 正式打包 10 分钟空闲态 CPU/能耗与 soak 实机复测仍保持开放，在实机采证完成前不宣称 Phase 2 门禁关闭。

### Phase 3 — 渲染层能耗

58 处 `requestAnimationFrame` 与 tuffex 的 refraction/backdrop 表面：窗口隐藏或面板不可见时必须 0 帧；用 CDP 统计帧数与合成层数做验收（已有先例：`perf(tuffex): stop refraction surfaces from stalling large panels`）。

> **2026-11-23 Wave 7 进展（PR `#2281` `fe5862dcc`）**：已在窗口失焦、隐藏、`<KeepAlive>` 失活、减弱动态效果或低电量（`html[data-low-battery-motion='1']`）状态下暂停 `TxBorderBeam`（含共享 `pulse-driver.ts`）、`HomePet`（`usePetController.ts` / `HomePet.vue`）、`TxMiko` / `HomeEmptyHead`（含 `v-if` 消除隐藏重复挂载）与 `useAuth`（惰性 focus-prompt 定时器），后台降至 0 Hz。打包 Electron 10 分钟空闲态 CPU/能耗实机复测随 Phase 1/2 一并排入 `v2.4.15-beta.15` 正式包出包后执行。

### Phase 4 — 常驻内存

WebContentsView 标签的 LRU 与快照冻结（已交付）+ 面板懒加载 + 索引进程 RSS 上限。

## 4. 不做什么

- 不为 3.0.0 引入第二套 UI 运行时，不在本轮评估 CEF/Tauri 的实现。
- 不把 native 能力拆成外部 sidecar 二进制（TCC/签名/公证成本，见 native PRD §2）。
- 不把 3.0 当作版本号重启：版本线随第一个内核化 PR 一起走发布脚本。

## 5. 可逆的保留项

唯一低成本的试水，将来若追求原生手感：**只给 CoreBox 做一个原生轻壳**（Raycast 式，只读 kernel RPC，面板仍留 Web 层）。它失败只丢一个壳，不影响 3.0 主线。前提是 Phase 1 把内核抽干净——这也是为什么 Phase 1 优先。
