# Outcome

修复应用搜索索引启动检查导致 `SEARCH_INDEX_READ_TIMEOUT:search-index-read-fast-*:3000` 的问题：完整性计数不占用交互搜索快通道，读取失败不会被误判为索引为空，也不会据此启动补建。

# Scope

- 应用 Provider 的启动健康检查、开发态 recent-backfill 判断，以及它们使用的搜索索引读服务。
- 区分「成功读取到零条」与「计数不可用」，保留真实 FTS 行数和磁盘应用探测作为补建依据。
- 同步受影响的调用方、现有回归覆盖和搜索索引健康检查契约；用实际 libSQL 读 Worker 验证查询通道隔离。

# Non-goals

- 不清空、重建或修改用户真实索引，不提高交互快通道的 3 秒超时，不移除真实 FTS 完整性判断。
- 不改变搜索排序、索引算法、扫描范围、watch 准入、补建开关和已有重试策略；不修复其他启动或网络告警。
- 不修改正在运行的开发实例，不提交、合并、推送或发布。

# Acceptance examples

- 启动完整性计数保留真实 FTS 结果，但不在交互快通道执行；超过 3 秒的该计数不使快通道读 Worker 被淘汰，也不阻止同一期间的应用搜索读取完成。
- 计数超时、读 Worker 不可用或冷却时，健康结果明确为计数未知；启动健康检查不按零条触发补建，recent-backfill 判断不因读取失败绕过近期完成保护，诊断也不将失败报告成真实零条。
- 在计数可读时，真实空索引或磁盘上存在有效但未入库的应用仍按既有门禁请求补建；健康或正在预热的索引不重复补建；watch/诊断的正常 meta-backed 计数与退出收尾保持原行为。

# Constraints and invariants

- 只在 `/tmp/tuff-app-index-startup-health-1003` 的独立 worktree 实现，保留源工作区的并发改动。用户已于 2026-10-03 确认独立工作区继续。
- 复用现有读服务和错误传播方式，不新增后台扫描、补建重试或读 Worker。
- 已有取证：同一真实库中应用 FTS 和 meta 均为 201 条；实际读 Worker 的首次 FTS 计数 3468ms，系统 sqlite3 约 0.85s。该测量证明不能用系统 sqlite3 的耗时代替 libSQL Worker，不宣称每次启动都必然超时。

# Verification expectations

- 定向回归覆盖计数失败后的补建决策、真实空/缺失应用的补建，以及读取隔离；检查受影响主进程类型契约。
- 在隔离环境运行当前源码的实际读 Worker：完整性计数与交互读取并发，观察真实结果与各自通道状态；不把 mock 回声作为运行态证据。
- Native Runtime 执行正式检查，新的只读 Verifier 独立判断全部验收项。
