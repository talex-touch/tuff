# 应用搜索索引健康检查

## 目标

应用启动健康检查必须识别真实索引缺失，但不能挤占 CoreBox 应用搜索的交互快通道，也不能把读取故障伪装成空索引。

## 查询通道

- 应用交互搜索继续使用现有快通道与 3 秒请求超时。
- 启动完整性检查和 recent-backfill 的完整性判断从现有非交互读服务取得真实 FTS 行数，不经过交互快通道；不以 meta 行数替代这两处决策所需的真实 FTS 计数。
- 不新增读 Worker。既有读服务的队列、超时、失败重建、冷却与退出关闭生命周期保持原有所有权。
- 日常 watch 路由和诊断的正常计数继续走既有 meta-backed 查询：FTS 为空时返回零，meta 缺失时保留真实 FTS fallback。

## 健康结果与失败处理

| 输入 | 健康判断与可见结果 | 允许的动作 |
| --- | --- | --- |
| 应用和真实 FTS 均有条目，磁盘探测无缺失 | 健康，计数为实际数字 | 不因健康检查请求补建；开发态近期完成保护生效 |
| 成功读出应用索引为空 | 明确不健康，计数为真实零条 | 在既有启动门禁与预热规则允许时请求补建 |
| 成功读出非空索引，但 watch 根中存在有效且尚未入库的应用 | 明确不完整，保留实际计数及缺失数 | 在既有启动门禁与预热规则允许时请求补建 |
| 计数超时、读 Worker 不可用、冷却或其他读取失败 | 计数未知，保留真实错误；不得报告为零条或健康 | 不依据该失败启动补建，不据此绕过 recent-backfill；不新增重试循环 |
| 索引仍在预热或本源扫描尚未完成 | 沿用已有等待/预热判断 | 不增加第二个扫描所有者 |
| Provider 尚未获得所需读服务或进入销毁 | 不发起新的完整性查询或补建 | 沿用初始化/销毁门禁 |

外部 IndexedSourceHealth 继续使用现有状态枚举。计数未知可以通过既有 degraded/warming 状态与明确原因呈现，不引入新的公共状态枚举，不把未知计数写成零条。

## 磁盘探测与补建不变量

- 磁盘探测仅用于既有启动完整性决策，不扩展为轮询或新增扫描。
- 只有符合原有平台与 manifest 判断的有效应用才构成缺失；路径规范化与无 manifest 的 `.app` 目录过滤保持不变。
- 保留补建开关、近期完成保护、设备空闲及渲染器就绪门禁、现有有界重试和扫描 mutation gate。
- 计数读取失败与真实零条必须走不同决策分支；成功读取恢复后仍按实际索引状况判断。

## 验证边界

- 回归验证失败计数不会造成误补建，并保留真实空索引与有效磁盘缺失时的补建行为。
- 用当前源码的实际 libSQL 读 Worker 验证完整性查询与快通道读取可并发完成；系统 sqlite3 只用于结果或查询计划校验，不能替代 Worker 耗时。
- 用户真实数据库仅可只读诊断，运行态验证使用隔离输出或隔离数据，不清空、迁移或重扫用户索引。
